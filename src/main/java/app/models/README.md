
# The Models Package #

Here are all the database models of the application.
We are using the Topsoil ORM to store and retrieve data from
a Sqlite database.

In Topsoil models are defined by interfaces and the
implementation is generated by Topsoil through
in the form of runtime proxies.

## Data-oriented model/value split ##

Every persistent entity is split into two types following a consistent, data-oriented pattern:

* A **model interface** named `XModel` (e.g. `UserModel`, `CampaignModel`) — the mutable,
  identity-bearing database root that Topsoil proxies.
* An immutable **value record** named `X` (e.g. `User`, `Campaign`) that aggregates the entity's
  *scalar* state into one `Value`.

A model holds its scalar state as a single value property `Var<X> state()` and exposes convenient
`zoomTo`-based getters that lens into it, so call sites keep using `model.name().get()` etc.:

```java
public interface UserModel extends Model<UserModel> {
    Var<User> state();
    default Var<String> username() { return state().zoomTo(User::username, User::withUsername); }
    default Var<String> password() { return state().zoomTo(User::password, User::withPassword); }
}
public record User(String username, String password) implements Value { /* withers + empty() */ }
```

Because the zoom getters call `state()` *directly*, the fluent query API can still query through them
(`db.select(UserModel.class).where(UserModel::username).is("dan")`) — the query resolver inspects the
getter's bytecode and reaches the underlying value column.

### Two consequences to remember ###

1. **Seed `state()` at creation.** A freshly `db.create(XModel.class)`d model has a `null` `state()`,
   so a zoom setter would dereference null. Seed it right after creating, exactly as we already do for
   the character sheet: `var u = db.create(UserModel.class); u.state().set(User.empty());`.
2. **Relationships stay on the model.** Topsoil values cannot reference models, so model-to-model
   links remain plain model properties (`Var<UserModel>`, `Vars<CharacterModel>`, …) alongside the
   single `state()` value. Purely-relational models (`PlayerModel`, `GameMasterModel`) therefore have
   no value at all.

`CharacterModel` is a special case: its aggregated state is the richer `sheet/CharacterSheet` value
tree (identity, vitals, abilities, skills, inventory, notes), so it carries `Var<CharacterSheet>
sheet()` instead of a flat `Var<Character>`.
